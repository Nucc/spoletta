# Spoletta

Visual builder and engine for agent workflows, modeled on OPM (Object-Process Methodology). Users draw flows of processes and objects on a board; runs execute them server-side with AI agents, bash scripts, people and built-in connectors such as GitHub and Slack.

## Layout
- `webapp/` Go 1.24 HTTP server, stdlib `net/http` mux, MySQL via `database/sql` (no ORM). One package `main`, one file per domain.
- `webapp/frontend/` React 19 + TypeScript + Vite + `@xyflow/react` (React Flow) + dagre. Plain CSS in `index.css`. All API calls and types live in `api.ts`. Pages are addressed by the URL's hash (`App.tsx`), each open in a tab of its own (`tabs.ts`, `TabBar.tsx`): only the open tab's page is mounted, the others keep their hash, and history entries carry their tab, so a page changing the hash in place must `replaceState` with `history.state`, never `null`.
- `worker/` Go service that runs the `pi` coding agent (npm `@earendil-works/pi-coding-agent`) and bash scripts for the webapp; manages per-run git workspaces (`workspace.go`): what a step leaves uncommitted is committed with the run, step and pi session as trailers, and once a run is over the webapp has its checkouts released (`releaseWorkspaces` in `webapp/workspace.go`), keeping branches and sessions, so a follow-up or re-run makes them again from the branch. `*.ts` there are pi extensions.
- Steps run through a sandbox the worker picks with `SANDBOX` (`worker/sandbox.go`): `process` (the worker's own processes, for development only; without `SANDBOX` set the worker doesn't start), `podman` or `docker` (a container per step, `sandbox_engine.go`, from `worker/sandbox.Containerfile`) or `kubernetes` (a pod per step, `sandbox_kubernetes.go`). A step's container sees only its own directories, parts of the worker's volumes mounted at the same paths, which a probe checks as the worker starts, and reaches only the webapp, whose proxies take it to its models, MCP servers, its credentials' services (`webapp/credentials.go`) and the internet hosts admins allow (`webapp/egress.go`). Its `HOME` is its run's (`runHome`). The worker never runs git in a checkout a step had, only fetches from it; what a step left is committed in a sandbox. `compose.sandbox.yaml` turns it on; `docs/SANDBOX.md` has the threat model, the mounts and Kubernetes' manifests.
- Any number of webapp replicas run on one database (`docs/REPLICAS.md`): what is kept is in MySQL, and each replica owns the runs, assistant's replies and follow-ups it starts (`replica_id`), saying it is alive in `replicas` (`replicas.go`); another replica a request reaches asks the owner through `replica_commands` (`commands.go`). What a replica that stopped (SIGTERM, or `REPLICA_TIMEOUT` without a heartbeat) ran is taken over by another and carried on (`adopt.go`), or with `RESUME_RUNS=false` ended. Steps' proxy tokens are in `proxy_grants`, hashed (`grants.go`). Nothing that must reach every replica may live only in one's memory.
- `compose.yaml` runs mysql + worker + webapp with podman compose. Secrets go in `.env` (never committed).

## Key concepts (start here before editing)
- Flow: a board of processes, objects, links. Kinds: job flow, module/procedure (reused by subflow processes, `modules.go`), struct (single reusable object, `structs.go`).
- Process kinds: agent, script, human, flow (nested board, `boards.go`), subflow (`calls.go`), connector (`connectors.go`).
- Objects have states, attributes, parts; links are OPM links (instrument, consumption, effect, condition on state). Runtime instances in `instances.go`.
- `engine.go`: executes runs; header comment documents the scheduling semantics. `runs.go` stores runs/steps.
- `run_board.go`: a run runs on its version (`runs.version_id`), never the board as it is: its walk and its steps' processes, prompts, settings, outputs, contracts, entries, unique attributes, stores and who decides its reviews come from the version's snapshot (`runBoard`, `flowRun.rb`; `runBoardOf` for routes about a run, such as deciding a review), so an edit reaches only later runs. Rows it records refer to board rows by id, with `process_id`/`object_id` NULL when the board no longer has one (`insertRunObject`), so read `process_ref`/`object_ref`.
- `publish.go`: a flow may publish one of its versions (`flows.published_version_id`), saved by Publish beside Save if the board changed, or an older one from the Versions panel (rolling back); neither changes the board, and restoring or undoing leaves it published. Which version a run takes (`runVersion`): the Run button, re-runs and trials (`trials.go`) the board as it is (saved first); schedules, `/v1` runs, webhooks' runs and record runs the version published, else the board as it is, and the API describes and checks what that version takes (`boardToRun`); a subflow process in a run of a published version runs its procedure's published version if any, else its board as it is, and in a run of the board its board as it is (`flowRun.published`, `calls.go`). `POST /api/runs` with `{"published": true}` runs it by hand. Runs on the version published don't hold the board (`lockBoard`). Setup files carry nothing of it.
- `diff.go`: what changed between two versions, or a version and the board (`GET /api/versions/{id}/diff[?to=]`, guarded on both): processes, objects, states, attributes, links, connections and starts, with fields before and after, and flow settings; layout only as a flag. Processes' samples (`trials.go`) are listed too, matched by id then by name on their process, but like layout don't make the board a draft. Matched by id, then what is left by name in the same place (a setup import makes over by name, giving new ids to what it renames), links and connections by their matched ends. Drives the Versions panel's draft flag (`publishedState.Draft`), the Changes panel and board highlights (`Diff.tsx`), and what the assistant changed.
- `run_list.go`: the board's run list (`RunList` in `Runs.tsx`), `GET /api/runs?flow=` a page of `runPage` at a time (`before=<id>`, "Load older runs"), filtered on the server by `status` (`waiting` is running with a step waiting for a person, the run's `waiting`) and `started` (each run one way: trial, re-run, record, api, webhook, schedule, run (a flow process's, item's or subflow's), else person; none picked lists all but trials); re-runs nest under what they re-run when both are listed. The filter is kept per flow in the browser; its search box opens the Data page on the query. The board keeps the open run apart from the list, which may leave it out. Each agent, script or connector step records how long it waited for its slots (`slot_wait_ms`, measured in `execute` before `personSlot`, since its row is made only once it has them) and which `try` of its process it is.
- `RunTimeline.tsx` (`timeline.ts`): a run's steps on a time axis in a window from its panel, a lane per process, overlapping steps on rows of their own; waits for a person hatched, a step's slot wait before its bar, long whiles with only people to wait for shortened; a flow process's lane unfolds its inner processes' lanes and the runs it ran as (fetched as it does, merged by process across items); a bar opens its step in the panel (a `step` `RunFocus`). `RunCompare.tsx` (`compare.ts`): two runs of a flow side by side at `#/flows/<id>/compare/<a>/<b>`, opened in a tab by picking the other run in the list after Compare… in a run's panel, from two `GET /api/runs/{id}`: how each started and ended and on which version, each process's steps paired by what they took then by order, what they took and handed back and the objects' last values, differing lines and fields marked. `scripts/run-views.ts` (`npm test`) checks both helpers.
- `shortcuts.ts`: the one registry of keyboard shortcuts, each with its keys (mod is Cmd or Ctrl) and where it works; pages answer the page-wide ones through `useShortcuts` (`Keyboard.tsx`, a capture-phase listener on `window`), never a `keydown` listener of their own (a field's, a panel's or a dialog's own keys stay theirs, the find box's, the palette's and a note's matched against the registry), `?` lists the registry (`ShortcutSheet`) and toolbar titles and the palette show keys from it. None is taken while typing in a field or with a dialog open but Cmd-K, so a new shortcut is a registry entry plus a handler. `CommandPalette.tsx`: Cmd-K anywhere, a modal `<dialog>` so it opens over other dialogs: flows, procedures and structs (`GET /api/flows`), the open flow's latest runs, the pages and the settings' tabs (`tabsFor`), fuzzy-ranked (`fuzzy`, `rank`), recent picks first (localStorage); a page opens in the tab showing it or a new one. The page shown adds its own items through `usePaletteSource`: the board its actions (save, publish, run, try, find, views, the run's timeline, log and compare, adding each block) and opening its flow's runs in place. `find.ts`, `BoardFind.tsx`: Cmd-F on a board finds processes, objects and states by name, the board shown and those inside it first; Enter goes to the next, entering its board (parts on their object unfolded) and centring it. `scripts/keyboard.ts` (`npm test`) checks the helpers.
- `Toolbar.tsx`: the board's toolbar keeps Save, Publish, the problems count and Run in reach, Run labelled with a menu beside it (the board as it is, the version published, starting with inputs, trying the selected process), and the board's views (versions, code, OPL, flow settings, MCP servers, Data, Records) in one menu, which takes Group into flow and Tidy up, then Save and Publish, as the window narrows (`COMPACT_TOOLBAR`, `NARROW_TOOLBAR`, which `index.css` repeats), so it keeps to one row; on a phone (`PHONE_TOOLBAR`) what opens under a button spans the window and the others on the board show as their count. Everything in its menus is in the palette too, and the board's shortcuts wait while a menu has the focus (`typing`).
- `logs.go`: each run's log (`run_logs`), read in its Logs window (`RunLogs.tsx`, opened from the run's panel): when it started and who or what started it, each step starting and how it ended with what went wrong, and how the run finished, logged with `runLog`, which writes the server's log too; and the lines the worker logs of each step it runs (`worker/logs.go`: getting its workspace ready as it goes, each repository fetched and cloned with git's progress and what it waits for (`worker/git_progress.go`), which the step shows in the run's panel while it goes (`StepActivity` in `Runs.tsx`), where it worked, how pi or bash was started, their stderr, the outcome; never prompts, keys or tokens), streamed with an agent's conversation and with what a script prints. As it starts the webapp logs what it did (database, migrations, runs it ended, sign-in, whether the worker answers) and stops naming the step that failed.
- `changes.go`: what a step changed in its repositories, each file with its patch, from the commit it started from to the one it or its follow-ups left, which the worker reads from the shared repository where it keeps the runs' branches (`worker/diff.go`, `POST /workspaces/diff`), never from a step's checkout. Shown beside an agent's conversation, or a script with its inputs and what it prints, stdout and stderr streamed as it runs and kept in `run_step_output` (`script_output.go`, `worker/output.go`), in the step's Terminal window (`StepTerminal.tsx`, opened from the step in the run's panel), which shows everything in full on one scrolling page; while an agent goes, the files come from its edit and write calls instead.
- `loops.go`: a loop's circuit breaker. Each pass keeps the pass it came from (`pass.fork`), back to the last a person started, and a digest of what each process took. A process about to go round a loop with no person deciding in between (a failure connection leading back to what failed, say), past its `loops` setting or on just what it took on an earlier round, waits on a step of kind `loop` for someone who may edit the flow to say whether it goes on (`POST /api/runs/{run}/steps/{id}/loop`), shown on the board as a review is; stopping fails the run unhandled. Loops a reviewer's `rounds` bound, or a person's decisions drive, don't count.
- `inbox.go`: the Inbox page (`#/inbox`, `Inbox.tsx`, counted in the tab bar, polled): every step waiting on the person signed in across the flows they see, newest first, reviews and inputs they may decide and loop questions of flows they may edit (`decidesStep` in `user_roles.go`, which the run's panel and who is told use too), each review's roles and instructions from its run's version (`runBoard`); each opens the board on its run with its review showing (`#/flows/{id}/runs/{run}/steps/{step}`). `notify.go`: telling people a step waits on them, reminding them every human process's `remindAfter` while it waits (each round claimed by counting it, `run_steps.reminded`, and moving `remind_at` on from now; none at or after `expires_at`), and telling whoever started a run it failed if they asked (`users.notify_*`, Account tab), by email (`mail.go`, `SMTP_*`, stdlib `net/smtp`) and a Slack DM from the Slack connector's app, linking through `PUBLIC_URL`; admins only when nobody else may decide. Each message claimed once across replicas in `notifications` (sent time; one a stopped replica claimed is sent by another). A human process's `waitAtMost` (its run's version's, as `remindAfter`) fails it past that (`run_steps.expires_at`, claimed by the guarded `waiting` update, then `eng.decide` with `expired`), so a failure connection from it can handle it. Every replica sweeps each second; without sign-in nobody is told.
- `reruns.go`: re-running an ended run from one of its processes as a new run on the board as it is, even of a run of the version published: what came before the process is copied as a `copied` step, the process starts with what it took (editable in `RerunDialog.tsx`), and it and what follows run anew (`walk.resume` in `engine.go`), on a branch starting from the commit the run's branch was at as the process started.
- `adopt.go`: runs outlive their replica. As `endStopped` finds runs a stopped replica walked, a live one claims each once (a conditional update of `runs.replica_id`, with the runs going inside it; `run_moves`) and walks its version again (`carryOn`), taking up the steps it stored as it comes to them (`liveRun.past`: by process in id order, the same inputs first), so every frontier is rebuilt, with its passes, rounds and loops: a waiting review or loop question waits again as the same step (deadlines, inbox, notices go on), one decided while no replica walked it is taken in from `run_steps.decision`, which the decide route writes and the walk clears once it recorded what follows; an agent, script or connector step going is lost (`stepLost`) and goes again on what it took if its retries let it, else fails to its failure connection. Steps taken up record nothing anew; a flow process's board is walked again, an ended child run only to rebuild what came of it; a subflow takes its child run's version (`calledAs`). Runs keep what they carried in (`runs.carried`) and whether they took the published version (`runs.published`), agents' instructions per object decided on are on `run_objects.instructions`. What a replica records of a run another took over is refused (`errNotWalked`: `startStepAs`, `finishStep`, `endWalkedRun`). It starts once the replica listens (`adopter`), so steps going again reach its proxies, and goes in the background once at a time (`adoptInBackground`), so the heartbeat never waits for it. `RESUME_RUNS=false` interrupts as before; trials and runs without a version are always interrupted. The run panel shows its `moves`.
- `trials.go`: trying one agent, script or connector process alone from its panel (`TrialDialog.tsx`): a trial is a run of the flow on the board as it is, never the version published (`runs.trial_of`) in which only it runs (`walk.try`), on inputs the person gives, whatever its conditions, unhandled if it fails. It really runs (posts, pushes), on a branch of its own, under spending limits and audit, but stores nothing real runs see: `finishStep` stores no persistent values or shared records for it, it has no schedule (`$SINCE`), the Data page leaves it out unless the query names the `trial` facet (`withoutTrials` in `rundata.go`), the run list unless its filter picks trials (the open one stays listed), the Activity page and the flow list's health and last run count none (what it spent still counts toward cost), and it isn't re-run. What a process is tried on can be saved as named samples (`process_samples`), part of the board: `snapshot`, paste and setup files keep them; an import without a process's `samples` keeps its own, and the assistant never sees them.
- `shared.go`: a struct's object marked shared keeps one store of records every copy of it reads and writes, in whatever flow (`objects.store_id`, `shared_records`), told apart by a unique attribute. A process only generating it adds and refreshes records keeping their state; one taking or querying it too moves them to the state it comes out in. Queries pick what gets worked on; no run claims or releases a record. People add, correct (fields, state) and delete records by hand on the Records page (`records.go`, `RecordDialog.tsx`); a hand edit replaces the record whole and refuses a unique value another record holds. `record_runs.go`: a person starts a flow querying the struct on records they pick from there (`RecordRunDialog.tsx`), a run per record (`runs.record_id`) on the flow's published version if any, whose queries of that store read the record alone; a re-run reads it again. The dialog warns of records the query (the published version's) wouldn't select and runs going on them, but stops neither.
- `search.go`: the Data and Records pages' search, a faceted query (`status:failed -@Bug.state:fixed timeout`, `key:(a OR b)`, `key:>10`, `started:>now-1d`) run on the server over every stored run or record, with facet counts and sorting. Each column is a facet: the table's own bare (`status`), an object's attributes `@Object.attribute`. `frontend/src/query.ts` parses queries the same way, to colour them and rewrite them as facets are ticked; keep the two grammars in step: `testdata/search_grammar.json` lists queries and the tree each must parse to, checked against the Go parser by `search_grammar_test.go` and against `query.ts` by `frontend/scripts/query-parity.ts` (`npm test`, which the Go test also runs when Node 22.6 or later is installed). Both split terms on the same explicit set of space characters.
- `versions.go`: full-board snapshots, with the flow's settings (repositories, branch prefix, spend limit), which a run of the version works with and diffs compare, though restoring leaves the flow's as they are (history steps keep none); each version keeps a note, who saved it and why (`saving`: by hand, or `run`, `assistant`, `import` when saved on its own first, `template` for a flow's first, made from one). `history.go` undo/redo reuses them. Adding board data means updating `snapshot` and `restoreSnapshot`, and usually `paste.go`, `opl.go` and `diff.go`.
- `opl.go`: renders the board as OPL sentences, shown in the UI and given to agents.
- `notes.go`: notes on a board (top or a flow process's), boxes of Markdown placed, sized, coloured from a small set (`noteColours`) and pointing at a process or an object of the flow, or nothing (`notes`; `NoteNode.tsx`, the line to what it points at drawn only while both are on the board shown; added from the building blocks, the palette or N, deleted with the selection by `deleteSelection` and `removeNodes` at once, counted in the Undo notice, a new one left empty dropped without one, Escape deselecting them in `closeOpen`). Board data: `snapshot`, history, paste (notes on boards copied go along, pointing at what went too) and setup files (`notes:` per board; absent keeps the board's, `[]` clears them, the same text keeps a note's id) keep them, and the diff lists them, matched by id then text, but like samples and layout they don't make a draft; no run, OPL or agent reads them. The assistant sees them in its setup file.
- `presence.go`: who else has a board open, by their initials in its toolbar (`Presence.tsx`): each tab says so every 5s (`PUT /api/flows/{id}/presence`, a `board_viewers` row by flow, person and tab, gone after 20s unheard or at once when it leaves; seeing the flow is enough, `neededAccess`), and is answered with the others, editing if they changed the board in the last minute, and whether another tab changed it since the change it gives (`since`), and who. Each history step added or gone to (`recordStep`, `goToStep` in `history.go`, which the board asks for with `?client=` after its changes, and imports and the assistant make) is a `board_changes` row; a tab told of another's loads the board again, once nothing is being typed, named or dragged on it, and says who changed it. Without sign-in nobody is shown, but tabs still reload others' changes.
- `assistant.go`: each flow's assistant, a chat at the bottom right of the board (`Assistant.tsx`). pi in the worker, run without tools and kept to the flow by its prompt, replies with the flow as a setup file, which is imported through `setup_import.go` (saving a version first, which the reply keeps, `assistant_messages.version_id`); it may change only that flow. The board then highlights what it changed against that version until dismissed or edited. `assistant_runs.go`: it is told the runs of the flow a person's message names (`run 412`, `#412`, a run's link; a follow-up naming none keeps them; "Ask the assistant" in a run's panel and on a failed step writes such a message to send), each within a share of a budget, cutting what steps that ended well handed back first and errors and decisions last and saying what it cut: how it started and ended, the diff of its version and the board, its steps with what they took and handed back, durations, costs, errors, decisions with instructions, and its log; besides, a summary of the latest runs, trials left out. Only the flow's own runs; steps' prompts left out, what looks like a key or token blanked, the prompt's tags defused in what runs produced.
- `problems.go`: what is wrong with a board before it runs (`GET /api/flows/{id}/problems`), a pure `boardProblems(snapshot, problemFacts)` over the board as it is, and the version published's errors beside. Errors are what a run can't get past as drawn (no start, a subflow running no flow or one gone, a connector process without its connector, operation or a required argument): `POST /api/runs` refuses them, listing them, for the board or with `published` the version published; schedules, `/v1`, record runs, re-runs and trials aren't refused. Warnings are what a run may get past or what is set up outside the board (an object nothing generates, a process nothing leads to, no model, a role nobody holds, a reminder at or past its time limit, a repository the flow lacks, skills, MCP servers, credentials, tokens): when unsure, a warning. What generates an object is `generatesOutput`, shared with the engine's walk. The board shows a count beside Run (`Problems.tsx`), whose list picks a node, and Run opens the list rather than start a board with errors.
- `templates.go`: ready flows to start from, `templates/*.yaml` (embedded), each `{title, description, setup}` holding one flow alone (no MCP servers, skills, structs or procedures, which an import would make over). `GET /api/templates` lists them with what each needs, worked out from it (repositories its processes name, connectors named by the connector's name such as `slack`, roles) and whether the app has it; `POST /api/templates/{id}` imports one through `importSetup` as a new flow named apart from every flow there is, owned as a new flow (`newOwner`), schedules off, a connector process given the first installed one of its connector or none (keeping operation and arguments), and saves a version with reason `template`. The flow list offers them (`Templates.tsx`), in place while it is empty.
- `Hints.tsx`: the board's help where it applies: a guide on an empty board, a line in the process, object and MCP panels, and a tip on what is selected or on a link drawn from a state (`BoardTips`), each hidden with its × per person in `localStorage` (`spoletta.hints.<user>`), shown again from the board's menu.
- `words.ts`: OPM's words said plainly where the UI names a link's role or a kind of flow, what it does first and OPM's term after ("uses (instrument)", "uses up (consumption)", "when it enters (event)"), a kind keeping its name ("procedure (reused flow)", "struct (reused object)"); used by the link's pickers, the diff, the sidebar, the flow list and the palette, the hints and the OPL panel ("Sentences (OPL)", with a key to its verbs) saying the same. OPL, the API and the setup file keep OPM's words; `docs/FLOWS.md` §2.5 lists both.
- `mcp.go`: MCP servers via OAuth, proxied per agent step at `/mcp/{id}`. Admins configure servers; each person connects them for themselves (`mcp_tokens`), and an agent step uses the connections of whoever its run is for (`runUser`). Their tokens, like model keys, credentials' and webhooks' secrets, are sealed with `SECRET_KEY` (`secrets.go`), rotated through `SECRET_KEY_SECONDARY` and `webapp seal-secrets` (`docs/SECRETS.md`); either key can come from a `_FILE`.
- `api.go`: other systems start flows over HTTP with an API key (`api_keys`, made in the settings' API keys tab, `APIKeys.tsx`), outside `/api/`: `POST /v1/flows/{id}/runs` runs the version the flow published (`publish.go`) and gives the run the objects its top board's processes take and none generates, by name, checked as what a person enters (`flowInputs`, `givenValues`); `GET /v1/flows/{id}` describes them as JSON Schema; `GET /v1/runs/{id}` returns what the run left of the objects connected to the end. They are given to the run as a subflow process gives its objects (`engine.start`'s `given`), recorded first as a step of kind `input`, so re-runs and unique values work as for any step. A person gives them by hand from Run's menu (`StartDialog.tsx`, `GET /api/flows/{id}/inputs[?published=true]`, `POST /api/runs` with `inputs`), on the board as it is or the version published, through the same `startGivenRun`. A key is its maker's: its runs are started by them (`runUser`) and it reaches only the flows they may run (`flowAccess`); an `Idempotency-Key` header makes a request sent again return the same run. Webhooks start runs through the same `startGivenRun`.
- `webhooks.go`: other systems' events starting a flow, added by those who may change it in its settings (`Webhooks.tsx`, `/api/webhooks`, guarded by its id), each at `/hooks/{token}` (outside `/api/`, the token compared byte for byte) with a secret sealed with `SECRET_KEY`, made and shown once or pasted. A delivery is checked in constant time by kind: GitHub's `X-Hub-Signature-256`, Slack's signing secret with its timestamp (five minutes either way), generic an HMAC of `[timestamp.][id.]body` (each header named covered, the timestamp five minutes either way) or the secret itself in a header; what isn't signed gets one terse 401, leaves no delivery, only `refused_count`, audited (`webhook.refused`) once a minute a webhook at each replica; each address is held to a rate on `/hooks/` (`hookLimiter`, per replica); the body is read under a deadline, at most 1 MB; Slack's URL verification and GitHub's ping answered; GitHub takes the events it names (`issues`, `issues.labeled`), refusing an event header its payload belies (`githubEventKeys`), Slack the Events API's. Taken once, by what the signature covers: a GitHub payload by its digest (the run's idempotency key, and `webhook_digests` for those ignored, 90 days), Slack's by event id, a generic one by its signed id (hashed keys, `idKey`), under `runs.webhook_id`; one refused takes nothing. Its mapping takes each object the flow starts from (`flowInputs`) from a dotted path into the payload, the whole of it, or a path per attribute, then `startGivenRun` checks it (`givenValues`) and starts the run as `/v1` does, on the version published, recorded first as an `input` step. Runs are for whoever added it, or last changed what starts them or turned it on (`created_by`, `runUser`), refused once they are removed or may no longer run the flow, and nobody's ones once people sign in. Each keeps its latest deliveries (`webhook_deliveries`) and the latest payload it took, sealed (Slack's `token` dropped), to write the mapping from; every signed delivery is audited (`webhook.delivery`) with fixed reasons, never the payload or the secret. Not in versions or setup files.
- `connectors.go`: services built into the webapp, each a set of operations in a file of its own (`github.go`, `slack.go`, `telegram.go`, `google.go`, `homeassistant.go`, `http_api.go`), listed in the settings' Connectors directory (`Directory.tsx`, logos in `logos.tsx`) beside curated remote MCP servers. A connector's hooks say how a call carries its token (Telegram's in the path, Google's a service account's key signing in), where it goes, what a success that failed looks like (Slack's `ok: false`), and what token it takes; what goes wrong names a call by its path, never its URL. Installed as an MCP server taking a token an admin sets (`mcp_servers.auth`, `connector`; the token is user 0's `mcp_tokens` row); the proxy answers agents' MCP requests for it itself, and a connector process carries out one operation as a step. `mcp_tools.go`: an agent process's picked tools of each server (`mcpTools`), which the proxy holds it to, filtering `tools/list` and refusing other calls; without picking, all of an MCP server's tools and a connector's that only read. New connectors are code here, never plugins.
- `skills.go`: skills and commands people write in the settings' Skills & commands tab (`Skills.tsx`), each owned as a flow is (`owners.go`): its maker's until shared with a team or everyone. An agent process picks its skills (`processSettings.Skills`), which the worker writes as a `SKILL.md` each and hands pi with `--skill`; `/name` in its prompt, at a line's start or after a space, is spelled out from the command as the step runs, taking the rest of the line where it has pi's placeholders (`$1`, `$@`, `${1:-x}`). A flow uses only what its owner may (`flowSkills`), which the board offers and runs check (a picked skill it may not use fails the step; a `/name` it may not use stays as written, like a path); only the process's own prompt is expanded, never its inputs.
- `model_keys.go`: model providers' API keys, set by admins, by the environment variable pi reads each from; the worker says which providers its own pi config has and the variables they read (`worker/host_providers.go`, from `models.json`). `model_providers.go`: providers admins add in the settings (`ModelProviders.tsx`) beside the worker's own pi config: one pi knows (Anthropic, OpenAI, OpenRouter, …) with the models picked from pi's catalog, or a custom one such as an AI gateway (URL, API, model IDs); its key saved here or kept in a vault that puts it in the webapp's environment, where only the variable's name shows. Every agent step gets them without keys, and the worker writes them into pi's `models.json` over the host's entries for the same providers (`worker/providers.go`), every provider pointed at the model proxy. The default model a process without its own uses is kept here once a provider is added.
- `git_tokens.go`: each step working on repositories gets a git token for them (`gitTokens.forWorkspace`), sent beside its workspace and never stored with it: a GitHub App's installation token for the run's repositories, lasting an hour (`GITHUB_APP_*`), or the instance's `GIT_TOKEN`. The worker writes it to a 0600 file in the step's private directory and points every git of the step at `git-credential.sh` through `GIT_CONFIG_*` (`worker/git_credentials.go`); a step that would outlive its token is stopped as it ends.
- `credentials.go`: a service's secret scripts and agents use without seeing it (a Jira token, an internal API's key), kept by admins in the settings' Credentials tab (`Credentials.tsx`): a name, an https base URL, how the secret goes (a header from a template such as `Bearer {secret}`, basic auth, a query parameter), the secret sealed with `SECRET_KEY`, never sent back; everyone's or given teams' (`credential_teams`). An agent or script process picks its credentials (`processSettings.Credentials`, `credentials:` in the setup file), only those its flow's owner may use, as skills (`flowCredentials`; one it may not fails the step); a step, and a follow-up of it, takes the picks of its run's version (`runBoard`), and the version diff names them. Its step gets `CREDENTIAL_<NAME>_URL` for each and one `CREDENTIALS_TOKEN` (a `proxy_grants` grant, revoked as the step ends and on a timer); the proxy at `/credentials/{id}/...` checks the grant, the pick and the owner at each call, joins the path to the base URL refusing `..`, `;`, dot-and-space segments (before a `:` too), non-ASCII, encoded slashes and `%`, passes on only an allowlist of request headers (`credentialPassedHeaders`) and those the credential names (`_` read as `-` against the denylist), swaps the token for the secret (a query parameter first in the query), never follows redirects (one within the base URL becomes the proxy's, the secret is taken out of others; `Link` the same), asks for answers uncompressed (gzip once is read, up to 256 MB, else 502) and in UTF-8, US-ASCII or ISO-8859-1 (no `Accept-Charset` or `Accept` charset goes on; another charset or a UTF-16/32 byte order mark is a 502) and blanks the secret out of them, headers and body, in each form it could be echoed in and any eight characters in a row of one (`credentialRedactor`, `redactor`), passes back only an allowlist of answer headers (`credentialAnswerHeaders`), and logs each call in the run's log and the audit log. A step's tokens are blanked out of what is kept of it (script output, conversation, worker log, result) and of the worker's own log (`worker/logs.go`), also in base64 and as basic auth's `user:token` (`tokenForms`). An edit changing the base URL, even only its path, or moving the secret to another header, parameter or way needs the secret again.
- `llm.go`: the model proxy. Agents never get a model key: each agent step, follow-up and assistant reply gets a token (`llmBroker.grant`, revoked as it ends and on a timer), which pi sends as every provider's key to `/llm/{provider}/`; the proxy swaps it for the real key in whichever header carried it and forwards to the provider (its custom URL, the worker's models.json's, `LLM_UPSTREAMS`, or pi's own), streaming back and recording what each call took in `llm_usage`. Bedrock without a key signs in with the worker's AWS credentials instead.
- `spend.go`: what each model call cost, worked out as the proxy records it, at the price the worker's models.json or pi's catalog gives its model (`priceBook`; one without a known price counts at the largest models'), with what it read from and wrote to the provider's cache. `limits.go`: what admins let runs and people use, in the settings' Spending & limits tab (`Spending.tsx`): what a run may spend (a flow may set less, `flowSettings.RunSpendLimit`), counted with its subflows', items' and follow-ups' runs toward the run at their top (`rootRun`), past which the proxy refuses its calls and the engine stops it as failed (`engine.fail`); what a person may spend a month, past which their calls are refused; how many steps a person's runs have going at once (`engine.personSlot`, taken before one of the engine's slots); and how much disk a run takes, which the worker checks after each step (`worker/disk.go`).
- `audit.go`: the audit log, `audit_events`, written in the background: the tokens each step is handed for models, MCP servers, the internet, credentials and git, when the model, internet and credential ones end, each internet connection and credential call, refused calls and overspent runs, admins' changes to limits, internet hosts, model keys and credentials, and each webhook's delivery and change; never a token or a secret. Admins search it on the Audit log page (`Audit.tsx`, `#/audit`) with the same search as a flow's data.
- `activity.go`: the Activity page (`Activity.tsx`, `#/activity?days=7|30|90`), linked from the flow list, over the flows one sees (`seenFlows`, an id list worked out once, or for those seeing every flow the ones in the trash, left out): top-level runs going on and failed in the last 7 days, and over the period the top-level runs a day, how many failed and what they spent, by flow; the agent, script and connector processes failing most (counted where their steps ran, a retry each); human reviews' time to decide (`CUME_DIST` percentiles), changes asked (decisions with instructions) and rounds (decisions per run), and apart those timed out past `waitAtMost`, which are no decisions. Child runs roll up to their top and re-runs count as runs; copied, input and loop steps don't count. A run keeps what it and the runs under it spent (`runs.spent_micros`, `unpriced_calls`), added to as `recordUsage` in `llm.go` records each call, so spending is read per run, on the day it started. Days are the viewer's (`periodOf`): the database gets each day's start and buckets with `INTERVAL()`, needing no time zone tables. Its queries read only the period's runs and steps, through indexes added for them (`runs_started`, `runs_status`, `run_steps_kind`).
- `users.go`: people sign in over OpenID Connect, with the company's provider, Google or both (off without `OIDC_ISSUER` and `GOOGLE_CLIENT_ID`), the same user with either (`user_identities`); every `/api/` request then needs a session, and runs and human decisions record who. `user_roles.go`: a user's roles name the human objects whose processes they decide ("Finance handles Approve payment"), checked when a review is decided. Not to be confused with a link's role (instrument, consumption). Admins add, remove (soft: `removed_at`) and promote people in the settings (`#/settings`, `Settings.tsx`).
- `teams.go`: teams of people, made by admins and team managers. `owners.go`: every flow, procedure and struct is global, a team's or a user's (its maker's by default); `guardFlows` turns away requests about flows the user doesn't see, for everyone (admins and no sign-in too, for the trash), finding the flow from the path, query and JSON body (and a diff's `?to=` version), so a new route with a new kind of id needs an entry there. Role holders see flows whose reviews they decide, read-only: a human object names their role on the board as it is, the published version, or the version of a run waiting on a person (`version_roles`, kept as each version is saved; `visibleFlows`), and a review is decided by the roles its run's version names.
- `trash.go`: deleting a flow, procedure or struct (`DELETE /api/flows/{id}`) moves it to the trash (`flows.deleted_at`, `deleted_by`), which is no one's to see, admins' included: `visibleFlows` and `flowAccess` leave it out (`liveFlows`), so do every list of flows and `guardFlows`, and only `/api/trash` reaches it, for those who may change it (`editableFlows`): restoring (`{name}` when a flow out of the trash took its name; schedules come round from then, copies follow it again) and deleting for good (`deleteFlow`). It starts no runs: `newRun` and `startChildRun` refuse it, reading its row as moving it there locks it, schedules skip it, the API and its webhooks don't find it. Moving one with runs going on is refused with `{running}` (409) unless `stopRuns`: its own runs are interrupted as Stop does, other flows' calls of it fail. Subflow processes running one fail saying so, `GET /api/processes` marks them (`trashedFlow`) and only a flow picked anew is checked (`checkCall`); copies of its objects are their flows' own (`copyReason`, `objectColumns`), as once it is deleted. Setup files, imports and the assistant leave it out, freeing its name; importing over a flow keeps its links to one (a subflow process without `runs`, an object without `copyOf`). Every replica empties the trash of what it kept `TRASH_KEEP` (30d), each flow claimed by locking its row (`SKIP LOCKED`). A new query listing flows must leave it out. Frontend: the Trash page (`Trash.tsx`, `#/trash`); a delete that can't be undone asks with `Confirm.tsx` (`useConfirm`), never `window.confirm`, and one that can (the board's, through `history.go`, or to the trash) asks nothing but shows `UndoNotice.tsx` ("Deleted X · Undo") until the next change; the board first records a history step, whose `held` says whether a run (a trial's too) holds the board, refusing undo, and then asks instead.
- `tags.go`, `favourites.go`: tags those who may change a flow, procedure or struct give it (`flow_tags`; carried by setup files, a struct's on its object, not by versions; the assistant keeps them when its reply leaves them out), and the flows each person stars (`favourite_flows`, user 0's without sign-in; starring needs only seeing the flow, `neededAccess`). The flow list (`FlowList.tsx`) searches names and tags as one types, narrows to a tag, puts favourites first and shows each flow's health (`flowHealths`: its top-level runs of the last 7 days, failed, and going on); `listFlows` and `describeFlows` read it all in a handful of queries, never a query per flow.
- `docs/FLOWS.md`: how to author flows for a user (OPM, run semantics, step contracts, worked setup-file examples). Read it before generating a flow.

## Database
- `database.go`: where the database is, per environment (development, staging, production, picked by `APP_ENV`), in the file `DB_CONFIG` names, else `config/database.yaml` (gitignored; copied from `config/database.yaml.example`, looked for in the working directory and the one above), else the `DB_*` variables. Each value is a `text/template` taking `{{ env "NAME" "fallback" }}` and `{{ file "/path" }}`; the file is read and filled in again for every connection opened, never kept, so a password rotated in its file is used without a restart (connections live 5 minutes).
- Migrations in `webapp/migrations/`, numbered SQL files run by goose (`github.com/pressly/goose/v3`) as the webapp starts, each once, recorded in `goose_db_version` (`migrations.go`, embedded in the binary). A schema change is a new file (`00003_add_x.sql`), never an edit of one that ran; MySQL can't roll back DDL, so keep each small. `00002_schema.sql` is the whole schema as it stood when migrations began; `00001` runs the code that kept it before then (`legacy_schema.go`, frozen) on a database from that time. Neither can be undone.
- Every new migration has a `-- +goose Down` section undoing its Up (dropping what it added, putting back what it changed), so an older webapp can run on the database again: `webapp migrate down-to <version>`, run with the webapp that has the migrations to undo, before deploying the older one; `webapp migrate status` lists what ran. Going down past a migration without a Down is refused. Where undoing loses data (a dropped column's values), say so in a comment above the Down. `docs/MIGRATIONS.md` has the rules and an example.
- What must happen on every start, not once, such as taking over or ending runs a stopped replica left running, goes in `endStopped` (`replicas.go`), never in a migration; it touches only what replicas no longer alive own, never another's.

## Build & test
- Frontend: `cd webapp/frontend && npm run build` (runs `tsc -b`). Dev: `npm run dev` proxies `/api` to :8080.
- Go: `cd webapp && go build ./... && go vet ./...`; same in `worker/`.
- Unit tests: `cd webapp && go test .`
- E2E tests: `cd webapp && go test -race ./tests` need compose MySQL on 127.0.0.1:3306 (`podman compose up -d mysql`; `MYSQL_PUBLISH` and `TEST_DB_ADDR` move it); otherwise skipped. They build and start the real webapp, drive it over HTTP, and fake the worker. New behavior gets an e2e test in `tests/*_e2e_test.go`.
- Full stack: `podman compose up --build`, app on http://localhost:8080.
- CI (`.github/workflows/ci.yml`) runs all of the above but the full stack on every push to main and pull request, the e2e tests on a MySQL service like compose's.

## Conventions
- Comments are plain English prose explaining what and why, in the domain's vocabulary; every file starts with one describing its concept. Match that.
- Commit subjects: one plain sentence in imperative mood describing the user-visible change, no prefixes (e.g. "Undo and redo changes to the board with Cmd-Z and Cmd-Shift-Z"). Body optional, prose.
- Keep dependencies minimal; prefer stdlib.
